## 0. 赶时间先看：决策树

**时间点就是一切。发现中招后的第一个动作，决定了最多能拿回多少。**

```
发现文件变成 .L0CK3D
   │
   ├─ ① 立刻断网（拔网线/断公网映射），但【不要重启、不要关机、不要 kill、不要重装】
   │     查加密器进程是否还在：ps / ls -l /proc/*/exe | grep deleted
   │
   ├─ 进程还在 ──────────────► ★ 最优解：kill -STOP 冻结 → 导出进程内存
   │                            → 取 48 字节 AES 会话主密钥（IV16 + KEY32）
   │                            → 解开每个文件尾部 48B 记录 → 全量无损解密
   │
   ├─ 有 Btrfs 快照 ─────────► rsync 从快照回写即可全量恢复
   │                            （#snapshot 目录为空 ≠ 没快照，查 /volume1/@sharesnap/）
   │
   └─ 进程已退出、无快照 ────► 本文主体：Btrfs 旧 extent 无密钥重组（部分恢复）
                                另可叠加：空闲区雕刻、数据库数据页抢救、公开源重建
```

**关键反例**（社区已验证）：有人「没重启、uptime 149 天」，但加密结束 30 小时后全扫 13.5 GiB 内存（含 6 个 zram）**0 命中**；另一人 8 小时后就扫不出了。**「不重启」只是必要非充分条件，决定性条件是加密器进程还活着。** 载荷跑完会自删，密钥随进程内存一起消失，之后补不回来。

## 2. 加密格式与密钥体系（实测，不是抄报告）

### 2.1 文件尾部 588 字节布局

抽 4 个真实加密文件（601B 小图、513KB 截图、2.45MB 照片、12.5GB 视频）逐字节比对，`磁盘大小 = 原始大小 + 588` 精确成立，结构完全同构：

| 偏移         | 长度      | 内容                                                                   | 实测特征      |
| ---------- | ------- | -------------------------------------------------------------------- | --------- |
| `0..48`    | 48      | AES-256-CBC 包裹的每文件记录：`ChaCha key32 ‖ nonce8 ‖ nonce8`（nonce 重复一遍作校验） | 高熵、零填充为 0 |
| `48..304`  | **256** | **RSA-2048 公钥加密的会话密钥密文**                                             | 高熵        |
| `304..568` | **264** | **全零填充**（此前公开资料未记录这一段）                                               | 熵 = 0     |
| `568..572` | 4       | 会话标记（单次运行标识，每台机器不同，公开无风险）                                            | 4/4 一致    |
| `572`      | 1       | 加密档位：`0x24` 整文件 / `0x25` 分段 / `0x26` 前 1MiB                          | 实测三种都有    |
| `573`      | 1       | 分段百分比（仅 `0x25` 用）                                                    | 实测 10     |
| `574`      | 1       | `0x20` 真加密 / `0x21` 诱饵                                               | 实测 `0x20` |
| `580..588` | 8       | 原始文件大小（uint64 小端）                                                    | 与差值吻合     |

### 2.2 两种「听起来矛盾」的说法其实都对

- 厂商报告说「文件密钥用 **RSA-2048 公钥**包裹，没私钥解不开」——对应 `[48:304]` 那 256 字节，**属实**。
- 社区救援案例说「从**内存**取一把 **AES 会话主密钥**就能全解」——对应 `[0:48]` 那 48 字节，主密钥在加密进程存活期间常驻内存（样本全局指针 `0x5427f8`），**也属实**。

**这是同一程序的两条并行路径**：攻击者用 RSA 私钥走 A 路；受害者在进程还活着时走 B 路。所以网上两种误判都要避开——「有 RSA ⇒ 只能交赎金」漏掉了内存旁路；「没 RSA 私钥就完全没救」又忽略了进程存活时的机会。**但 B 路只在进程存活时存在**：载荷跑完自删后，A 路私钥拿不到、B 路 48 字节随内存蒸发，全盘解密才真的做不到。

### 2.3 档位决定可恢复性

| 档位     | 行为                        | 旧 extent 路线恢复率（社区统计）      |
| ------ | ------------------------- | ------------------------- |
| `0x26` | 只加密前 1 MiB                | 约 99.8%                   |
| `0x25` | 分段加密头/中/尾共约 12%，约 88% 仍明文 | 约 98.2%                   |
| `0x24` | ≤1 MiB 小文件整文件加密           | 约 1.7%，基本救不回（只能靠空闲区雕刻碰运气） |

社区大规模案例：合计约 74% 文件 / 73% 字节；另一例 20.6 万文件 / 1TB 总体 65.4%（照片 97.9%、视频 99.4%、>128MB 视频 80.8%）。**小文件是这类勒索的固有损失，不是工具不行。**

## 3. 处置大方向（三步）

1. **保现场**：断网、别重启别 kill、别删 `.L0CK3D`、别清空回收站、停用一切会写盘的服务。旧数据块正是靠密文文件「拽着」才没被回收。
2. **判路线**：按 §0 决策树确认能否取内存密钥 → 有没有快照 → 否则走旧块路线。**别急着追新工具**，先核对它的适用前提（尤其是「加密进程是否仍在运行」）；前提不满足的工具，再新也没用。
3. **只读导出 + 逐块验证 + 断点账本**：所有结果写到 NAS 以外的盘，NAS 端只做只读查询和读取；逐文件记录完成状态，断电或换盘后能续跑；把「精确恢复并经校验和证实」「推测候选」「失败」分开统计，不混为一谈。

> 一条红线：**不要在生产 NAS 上安装或运行第三方恢复助手、来源不明的「解密器」**。安装包、日志、缓存、扫描索引都会写盘，可能覆盖还没抢救出来的旧数据块，直接降低恢复率；闭源二进制以 root 运行同样不可取。

## 4. 常见误区与已被证伪的说法

### A. 关于「能不能解密」

| 说法                         | 验证与结论                                                                                                              |
| -------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| 有通用解密器 / 执法缴获了密钥           | 截至 2026-11-06 全网与社区情报复查：**无**通用解密器、无私钥或主密钥泄露                                                                       |
| 网上新出的工具或教程一定更管用            | 大多是报道与复盘，不是新的恢复能力；真正新增的在线进程内存扫描工具，**硬前提是加密器仍在运行**，对已结束/已重启的设备不适用                                                   |
| 有 RSA 公钥 ⇒ 只能交赎金           | ❌ 漏了内存旁路。见 §2.2                                                                                                    |
| 没重启就一定能从内存捞到密钥             | ❌ 必要非充分。进程退出后 RAM / swap / zram / core dump 穷尽扫描（逐字节、多会话、多设备）可全部 0 命中                                              |
| 把加密器二进制恢复出来就能解密            | ❌ 会话主密钥由 `/dev/urandom` 运行时生成、只在内存、每次运行不同且不跨受害者复用；样本里只有 RSA 公钥。RNG 是 Hash_DRBG，不能从当前状态反推历史密钥                       |
| 通用文件恢复助手能救回被加密的文件          | ❌ 它看文件系统**当前**目录项，不会翻 Btrfs 旧 generation extent；对 ext4 上已删除的小文件，8 天持续写入后 `debugfs lsdel` 也会返回 0 个已删除 inode，元数据路径已断 |
| 删掉勒索信 / 清空回收站 / 做一次碎片整理没关系 | ❌ 任何写盘动作都可能覆盖尚未抢救的旧块；不要 defrag、balance、`btrfs check --repair`                                                      |

### B. 关于「数据还在不在」

| 说法                                     | 验证与结论                                                                                                                                           |
| -------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| 过了 8 天，盘上旧数据肯定劣化了                      | 用三件事实测：① 各档抽样文件是否仍存在、大小与会话标记是否吻合（35/35 通过）② 抽样文件逐 4K 块 CRC32C 与 Btrfs 校验和比对（`ok=256 bad=0` 8/8 通过）③ 卷使用率（仅 36%，旧块被复用概率低）。**结果是旧块完全健康，恢复上限没有下降** |
| 目录里 10 万+ 加密文件、普查账本才 2.5 万行 ⇒ 漏掉海量用户数据 | ❌ 绝大多数是群晖 `@eaDir` 索引缓存（`synoindex_media_info` 等）。排除后再做覆盖率终检：22,668 个真实媒体文件，**遗漏 0**。别把缓存当成漏掉的数据，也别把没扫到的当成救不回                                   |
| `sqlite3` 打不开 = 数据库没了                  | ❌ schema 页损坏但**数据页可以完好**。直接按 `page_size × page_count` 从空闲区提取整库，再从数据页抠字节配对，可以救回配置与记录                                                             |
| 表里「没数据」= 这份库没用                         | ⚠️ 先查过滤条件，表名大小写敏感写错会把能打开的库全判成无效                                                                                                                 |
| 旧根 bookend / `btrfs restore` 能翻出加密前状态  | ❌ `btrfs-find-root` 可列出数十个候选，但可用根的 generation 往往全在攻击之后；真正攻击前的根块多已被复用或不含目标子卷的 ROOT_ITEM，单文件走树取到的 extent 头部已是密文                                   |
| 空闲区雕刻能补回小照片                            | ⚠️ 技术上能（扫 283.88 GiB 空闲区，雕出 JPEG 6764 / PNG 3881 / MP4 636），但成品绝大多数是 48×48～256×256 的图标与缩略图，原名匹配率约 5%，**几乎没有真实照片**。别把它算进战果                       |
| 应用日志里可能夹带配置或凭证                         | 本例 78 万个日志文件搜关键字 **0 命中**，整批排除无损失。排除前先验一次，别凭想象                                                                                                  |
| 「那个配置文件」明明应该在那儿                        | ❌ 先核实文件到底存不存在。本例目标目录里根本没有该命名文件，真正的配置在别处；按想象列清单只会白费力气                                                                                            |
| 应用脚本目录能一起救回                            | ❌ 470 个脚本里 466 个是 `0x24` 整文件加密、`no_candidate`。脚本多是开源项目副本，**重装后从官方仓库/订阅源取回**更快（注意取回的是原版，不是本机改过的版本）                                               |
| 卷写满才想起来恢复                              | ❌ 卷被写满时旧 extent 会被复用，Btrfs 路线直接失效。**越早停写越好**                                                                                                    |

### C. 关于「验证与统计」

| 说法                    | 验证与结论                                                                            |
| --------------------- | -------------------------------------------------------------------------------- |
| 脚本报「成功」= 数据能用         | ❌ 必须逐块校验 + 文件结构验真：JPEG SOI+EOI、PNG magic、MP4 `ftyp`/`moov`、实际解码、SHA 对账           |
| 图片校验大面积失败 = 数据坏了      | ⚠️ 可能是校验脚本自己读错位置（把 `read(2)` 当成读文件尾），修正后 19/20 完整、MP4 12/12 `ftyp` 正常。**先怀疑校验器** |
| 账本里出现 `miss` = 文件损坏   | ⚠️ 可能是清单上传与远端读取的竞态：读到半截清单会吐空流，被误标后会永久跳过。整批空流绝不写断点，自动补跑                           |
| 系统分区镜像哈希与原盘对不上 = 镜像坏了 | ❌ 活盘持续写入，三次读取三个哈希是正常现象。用「确定性特征偏移抽查 + 文件系统 magic + 大小」验证内容，别拿之后任一时刻的原盘哈希否定快照      |
| 名字像恶意样本的临时文件就是样本      | ⚠️ 可能是自己上传的恢复脚本 base64。先解码再下结论                                                   |

## 5. 真正行得通的路（按收益排序，截至 2026-11-06）

### 5.1 ① 内存会话主密钥（条件：加密器进程还活着）★ 最优

发现后**不要重启、不要 kill -9**，`kill -STOP` 冻结进程 → 导出 `/proc/<pid>/mem` → 滑动窗口搜索满足「nonce 重复校验」的 48 字节（IV16 + AES key32）→ 解开每个文件 footer 的 `[0:48]` → 逐文件 ChaCha8 解密，**全量无损恢复**。

社区已有多个成功案例：虚拟化环境导出 16 GiB 内存镜像后全解 49 GiB 代码仓库；物理机冻结进程后救回 8.45 万文件 / 约 1.2 TB。开源参考：`soimy/c3rb3r-rescue`、`Benjamin-zlt/c3rb3r-baremetal-rescue`。**这是唯一能「直接全盘恢复」的路线，窗口只有一次。**

### 5.2 ② Btrfs 快照

快照在 `/volume1/@sharesnap/<共享>/GMT*/`，只读子卷改不动，rsync 回写即可全量恢复。`#snapshot` 目录为空不代表没有快照，务必单独查。

### 5.3 ③ Btrfs 旧 extent 无密钥重组（进程已退出时的主力）

**原理**：加密器**原地改写**文件、只加密几段；Btrfs 写时复制把改写内容写到新位置，而**未被加密的部分仍引用着原始 extent**，于是被改写段的原文整块留在盘上。按 extent 树把被改写字节映射回旧 extent，从块设备**只读**读出；开启数据校验和的共享还能用 Btrfs 自带 CRC32C 逐块证实。

**硬前提**：Btrfs（ext4 / ZFS 不适用）、卷未满、旧块未被后续写入复用、不要删 `.L0CK3D`。

**流程骨架**（形态示意，参数需按自己环境确定）：

```bash
python3 c3r_btrfs.py preflight <一个加密文件>        # 环境自检，先看 OK/WARN/FAIL
python3 c3r_btrfs.py gens    ...                     # 确定攻击代际 G_ATTACK
python3 c3r_btrfs.py csum    <若干文件> --g <G>     # 用已知原件做单文件逐块校验
python3 c3r_btrfs.py survey  <目录或清单> --g <G>   # 全量普查，输出状态账本
python3 c3r_btrfs.py extract @<清单> --g <G>        # tar 流导出；候选另加 --variant
# 本地端 c3r_local.py：解包、解码验证、挑最佳候选、打补丁换候选、统计
```

工具与指南：`crt106/c3rb3r-btrfs-recovery`（含 `patch` 候选工作流、兼容性说明、踩坑清单），另有 `hjs785053766/c3rb3r-btrfs-recovery` 等社区实现。


**本例结果**

| 项                                      | 数字                                                                       |
| -------------------------------------- | ------------------------------------------------------------------------ |
| 全量普查账本                                 | 25,619 个文件                                                               |
| `exact`（可精确恢复）                         | **10,462 个 / 219.81 GB**                                                 |
| `needs_inference`（大文件推测候选）             | 1,077 个 / 171.33 GB                                                      |
| `no_candidate` / `inplace_lost` 等（救不回） | 约 14,080 个 / 约 66 GB                                                     |
| 首个小样本验证                                | 100/100 exact；25,600 个 4K 块 CRC32C **全部一致**、0 坏块；单张 JPEG 完整解码 3000×4000  |
| 精确恢复导出                                 | **10,462 个 / 219.81 GB 全部落盘**，账本 1:1、0 缺失 0 校验错误                         |
| 完整导出清单                                 | 11,503 个 / 390.89 GB（排除 36 个纯日志后），分精确与推测两阶段串行                            |
| 照片视频细分                                 | 精确 10,357 个 / 214.7 GB；候选 1,030 个 / 169.9 GB；救不回 11,265 + 21 个 / 约 56 GB |

**必须把「精确恢复」和「推测候选」分开报告**：前者逐块 CRC32C 证实，后者是 `--variant` 推测出来的、带候选后缀，需解码验证才算可用。

### 5.4 ④ 空闲区雕刻 + 数据库数据页抢救（小型关键文件）

`0x24` 整文件加密的小文件（配置、数据库）在旧 extent 路线里判死刑，但原文往往还在**空闲区**：

- 扫空闲区搜文件头与特征串，按 `page_size × page_count` 精确提取整库；本例从 304 GB 空闲区命中数万处 sqlite 头，雕出 **25,361 个数据库文件 + 41 份配置候选**。
- **schema 页损坏但数据页完好**时，不必依赖 sqlite3 打开表结构，直接从数据页抠字节配对。本例从 **20,710 份**数据库代际拷贝中抢救合并，拿回配置文件内容（通知区、运行设置、数百条业务配置）、数百条任务定义与各类记录，并还原成可直接导入的格式。

> 一句话：**别因为「数据库打不开」就判定数据没了**。

### 5.5 ⑤ 公开源重建（脚本类文件）

脚本多为开源项目副本，正确做法是重装应用后从官方仓库 / 订阅源重新取回，而不是从密文里硬解。注意取回的是官方原版，不是本机可能被改过的版本。

### 5.6 ⑥ 非技术路径（别忽略）

手机本地相册与厂商云（NAS 常是手机单向备份的下游）、网盘网页端回收站与历史版本（删除后通常 30 天窗口）、电脑端同步客户端缓存、容器镜像重新 pull。**这些往往比逆向更省事。**

### 5.7 ⑦ 条件性的未来路径

若将来执法缴获 RSA 私钥或攻击者泄露密钥：解密脚本已就绪，需要 48 字节 `master.bin`（IV16 + KEY32）与本机会话标记，文件尾的 48B 记录和 256B 密文都完好，本地批量解密 600GB 量级约 2–3 小时。**在此之前不要付赎金。**

### 5.8 ⑧ 验证方法论（比「跑完了」更重要）

- 逐块 CRC32C 与 Btrfs 自带校验和比对
- 密文完好性抽样（存在、大小、会话标记）
- 文件级结构验真：JPEG SOI+EOI、PNG magic、MP4 `ftyp`/`moov`、实际解码
- 逐文件断点账本 1:1 核对，SHA 全一致
- **覆盖率终检**：排除索引缓存后确认没漏文件，避免把「没扫到」误当成「救不回」，也避免把缓存误报成战果

## 6. 工程层面的坑（自己写脚本跑恢复会踩）

1. 别删 `.L0CK3D`、别清空回收站、别 defrag / balance / `btrfs check --repair`。
2. **NAS 全程只读**，结果写外部盘；「上传清单 → 远端 extract → tar 流」时**必须等远端清单写完**再 extract，否则空流会被误标失败并永久跳过。
3. 外置盘设最低余量，满了就打断点优雅退出，绝不自动溢出到系统盘。
4. 断点账本是唯一真相；报告里精确恢复、推测解码通过、失败要分开写。
5. **批量文件操作会触发工具的「修改前备份」**，可能在系统盘产生与迁移量等大的副本；删除常常只是「移入回收站」（判据：目录文件数减少但剩余空间不变）；后台沙箱里的清理动作可能被静默拦截。**每轮小批量 + 前台核对磁盘实际余量**，别信上一次的计数。
6. 同盘 `os.rename` 一般不触发备份，跨盘迁移会；大批量迁移要边迁边清备份，把峰值压到单批大小。
7. Windows 下走 SSH 传 `/volume1/...` 路径要设 `MSYS_NO_PATHCONV=1`，否则被改写成本地路径；SFTP 可能被 chroot，绝对路径不可写。
8. 活盘做镜像，`sha256sum` 每次结果不同是正常的，用特征偏移抽查验证内容。
9. 第三方恢复类工具只在**离线镜像**上跑，不要装到生产 NAS。

## 9. 一句话总结

**能全量解密的窗口只有「加密器进程还活着」那一次**；错过之后，别再找解密器、别信恢复助手、别付赎金，把力气花在 **Btrfs 旧 extent 逐块重组 + 空闲区/数据页雕刻 + 公开源重建 + 手机/云/客户端缓存** 这几条实测有效的路上，并且**尽早停写、尽早只读、尽早断点导出**。本例在这条路上拿回 10,462 个精确恢复文件 / 219.81 GB，另把配置与数据库记录从数据页里完整抠了回来——但那约 1.4 万个 `no_candidate` 小文件，是这类加密的固有损失，诚实写在这里。
